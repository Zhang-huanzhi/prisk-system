# Prisk-System 推进大纲

### 一、 版本演进大纲

* **v1.1.0 规则知识库全集**
  * 补齐 20+ 条规则卡片（核心卡精写，候补卡粗写）。
  * 结构性预审：排除跨文件重分析，只留局部 AST 能做的。
  * 真实 PR 先导摸底：抽 10~20 个 PR 测命中与标注难度（**与最终评估集严格隔离**）。
* **v1.2.0 核心规则实现与三态引擎**
  * 筛选实现 8~10 条核心代表作（**必须硬性覆盖三大类**：语言异味、Django 契约、过程协同）。
  * 确立标准三态输出协议（`Hit` 出 Finding，`NotFound` 静默，`Unanalyzed` 记清单）。
* **v1.3.0 动态交互工作台与报告**
  * 运行时配置：规则开关、权重与阈值解耦。
  * 快照局部重跑：复用 Git/AST 上下文，只重算受影响规则。
  * Web 看板与报告导出：**报告强制固化本次运行的配置快照**（开关/权重/阈值），确保审查结论可复现。
* **v1.4.0 规模型实证打靶与权重校准**
  * 在**独立的正式实证集**上批量运行真实 PR。
  * 实证筛选：高噪规则降级或默认禁用。
  * 确立合理的默认基线权重（告别全 0 权重），产出论文实验数据。

---

### 二、 注意事项

1. **核心子集三类全覆盖**：v1.2 落地代码时，哪怕各做 1~2 条，也必须同时包含通用异味、Django 框架契约和过程冲击，绝不偏科。
2. **验证集与先导集严格隔离**：v1.1 摸底/调试用的 10~20 个 PR，与 v1.4 正式写进论文的实证集物理分开，防止“照着测试集调规则”引发学术质疑。
3. **审查报告必须固化配置**：导出的 Markdown/JSON 报告必须把“当时开了哪些规则、用的什么权重”一并封存，做到任何一次评分均可追溯、可复现。
4. **两次筛选分开**：v1.1 筛“局部 AST 能不能实现”，v1.4 筛“真实跑出来噪不噪、好不好用”。
5. **表述克制严谨**：说“结构匹配具备可复核性”，不说“百分百断定缺陷”；总分是“启发式复核优先级”，不是“Bug 概率”；弱标签仅作线索，必须人工肉眼核实。

---

### 三、 核心风险

1. **标注耗时爆炸 ➔ 规模兜底**：依据 v1.1 测得的单 PR 标注耗时倒推实证集规模；若时间紧迫，宁可缩减至 30 个深度核验的 PR，也绝不因追求样本量导致论文无法按期完成。
2. **实现卡死**：纸面卡片设计了依赖全局图分析的规则，导致 v1.2 无法用局部 AST 落地。
3. **实验零命中**：规则全定在极少发生的高危操作上，导致在优质开源 PR 中触发量为 0，实验没数据。
