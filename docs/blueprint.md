# Prisk-System 核心蓝图与技术规范
### 1. 核心定位与分析范围
* **定位**：面向后端代码变更的**风险辅助审查工具**，提供透明证据与启发式复核优先级，辅助人工审查，不代替人工做合格判定。
* **分析范围**：
  * **以 `base...head` 变更为分析入口，按规则读取必要上下文**；
  * 不做无目的的全库扫描，所有输出证据（代码切片、符号、指标）必须与本次变更直接关联；
  * 语言异味聚焦受改动行触碰的 AST 节点；过程规则扫描整个 Diff 增量元数据；框架与下游冲击按需读取关联上下文。

---

### 2. 系统两翼：实现与研究
系统由相互支撑的“工程实现”与“学术研究”两翼构成，缺一不可：

* **工程实现翼（软件工程闭环）**：
  * 遵循标准软件工程生命周期（需求分析、架构设计、代码实现、测试验证）；
  * 关注分析管道的健壮性与可用性——Git 增量与 AST 语法解析稳定、不崩溃、可交互、支持代码切片跳转与轻量快照重运行。
* **学术研究翼（科研与论文价值）**：
  * 核心回答**“为什么这个工具有用，为什么其风险刻画是可信的”**；
  * 核心资产不是单纯的代码堆砌，而是**成体系的规则知识库构建**、**变更风险的多维元数据打标**，以及**基于证据归因的可解释评分模型**。

---

### 3. 技术栈与支持范围分层
系统采用严格解耦的三层适配结构，不把局部适配泛化为“全能后端”：
* **语言层**：一期仅支持 **Python**。
* **框架层**：框架语义优先支持 **Django / Django REST Framework (DRF)**。
* **实证对象**：主验证与调优对象为 **NetBox**（后续可扩展类似真实开源项目）。
* **隔离原则**：
  * **通用 Python AST 规则**（语言规范与陷阱）；
  * **Django/DRF 专有契约规则**（路由、视图装饰器、ORM/原生 SQL）；
  * **项目特定配置**（测试目录结构、定制权限基类等）。
  * *三者物理隔离，新增项目适配不等于系统自动适配了其他框架。*

---

### 4. 三权分立：概念分类、Rule ID 与运行配置
这三者职责不同，严禁混淆：

1. **概念分类（研究与论文维度）**：
   * 三大知识域：通用代码异味（`code_smell`）、框架与安全契约（`backend_contract`）、变更破坏冲击（`breaking_impact`）。仅作为学术归纳、元数据标签和研究分类，不侵入工程标识。
2. **规则 ID（工程实现维度）**：
   * 采用统一的两段式物理标识：`<domain>.<rule_slug>`（如 `code.*`、`api.*`、`auth.*`、`data.*`、`config.*`、`workflow.*`）。保持现有工程命名稳定，不为迎合概念分类推翻 ID 设计。
3. **运行配置（执行引擎维度）**：
   * 指运行时传入的规则开关（`enabled`）、数值权重（`weight`）与检测阈值。
   * **元数据登记卡（Registry/Schema）仅代表规则的设计定义与理论依据，不等于系统已经在运行时支持动态调参。**

---

### 5. 判定状态与可解释评分哲学
系统具备严谨的认知边界，拒绝将“未警报”粉饰为“无缺陷”：

* **规则执行三态（Tri-State Execution Results）**：
  规则执行结果包含 `Hit / NotFound / Unanalyzed`，**其中只有 `Hit` 生成 Finding**：
  * **`Hit`（命中）**：检测到明确违背规则的特征，生成 Finding 并附带切片或指标证据；
  * **`NotFound`（未发现）**：在规则适配的上下文内未扫描出风险特征，不生成 Finding；
  * **`Unanalyzed`（无法分析 / 证据不足）**：因解析降级、语法不支持、缺少框架上下文或前置阶段数据缺失而跳过（记录未分析原因与对象列表，**不生成 Finding，但不等于扫描通过，更不等于代码安全**）。
* **评分的本质**：
  * 综合得分是**启发式的人工复核优先级参考**，绝非数学意义上的“Bug 发生概率”；
  * 处于试验期或默认权重为 0 的规则仅代表“规则感知已接入”，**不表示已证实其在当前项目中的实际风险度**；
  * 重大破坏性风险（如直接移除核心鉴权）支持“一票抬升”复核优先级。

---

### 6. 核心工作流与交互底线
```
选择本地仓库 ➔ 选定 base...head 
  ➔ 提取 Diff 与必要结构上下文 
  ➔ 按当前配置执行已启用的规则 
  ➔ 产出 Hit 生成的 Findings（附带证据切片）与 Unanalyzed 汇总
  ➔ 计算透明启发式复核分 ➔ (可选) 导出快照报告
```
* **运行时调优闭环**：
  * **复用 Git 提取和上下文快照，仅重跑受影响规则，不必重新读取仓库**；
  * 仅调整权重时直接重聚合评分；调整阈值或开关时仅局部重算对应规则。
* **证据可追溯**：命中 Finding 必须包含清晰的上下文（Before/After 代码切片、行号），支持在界面中直接定位对应代码。

---

### 7. 后续演进视野（保持学术克制）
* **云端接入**：从仅支持本地分支对比，演进为按需抓取 GitHub / GitLab PR 临时上下文。
* **机器学习（ML 探索项）**：
  * **前提**：必须具备真实、可追溯的历史缺陷/回滚标签、科学严谨的数据集划分及外部项目验证；
  * **定位**：仅用于探索规则权重的校准优化；**规则引擎永远优先且独立，ML 属于可选、可独立关闭的辅助实验**。
* **大模型（LLM 辅助项）**：
  * 仅用于对已有 Finding 和 Diff 切片进行辅助性的“变更意图推断”与“审查评语草拟”，不作为底层漏洞裁决器。

---

### 8. 规范基准声明
> **本蓝图定义目标系统；具体能力以实现、测试与验收记录为准，新增架构能力单独设计，不回填为已有功能。**
