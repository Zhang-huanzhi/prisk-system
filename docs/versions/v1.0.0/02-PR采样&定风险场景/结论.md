# 结论

查询日期：2026-10-28。`saleor/saleor` 保留为对照项目；主实验项目最终确定为 `netbox-community/netbox`。

抽样 40 条已合并 PR，来自 4 个时间段和 27 名贡献者，小、中、大改动各约三分之一。Dependabot 和 Renovate 已排除。40 条的基础版本和目标版本都能在本地恢复。去掉只改文档、静态资源、模板或锁定文件的 4 条后，可分析样本 36 条。记录在 `saleor-trial.jsonl`，汇总在 `场景表.md`。

纳入规则的场景是两类：

- **接口行为。** 25 条可分析 PR 改了 GraphQL 模块、schema 文件或 webhook。小、中、大改动里都有。需关注 11 条，未标记 11 条。相关 Python 文件都能被 `ast.parse` 解析。
- **数据与事务。** 15 条改了模型、迁移或事务边界，三种都出现了不止一次。需关注 7 条，未标记 5 条，不确定 3 条。解析成功率同样是 100%。这 15 条里没有小型 PR，模型、迁移和事务变化集中在中等和大型 PR。

先不纳入、只留作案例的是两类：

- **认证与权限。** 只有 4 条，而且都是大型 PR，例如仓库实现、移除旧后台和更新演示数据。权限路径本身只明确出现 1 条。数量不够，也不能看成反复出现的一类小变化。
- **配置与异常。** `saleor/settings.py` 出现了 10 条，但是同一文件。异常模块只有 2 条。另有 6 条只改到 `except` 行，没有算进场景次数。

测试协同不占这两类名额。36 条业务代码有变化的 PR 里，25 条同时改了测试，11 条没有。

这一阶段的语法检查用的是 Python 标准库 `ast.parse`，确认目标版本上的 `.py` 文件能解析。框架级的结构对齐留到下一阶段。评价证据也先分开存放：36 条可分析 PR 里，13 条能把审查评论对应到之后改过的文件，19 条没有这种评论，4 条评论对不上后续文件。CI 结果 34 条已经取不到，只有 6 条还能看到成功或失败。合并后修复没有一条能从 PR 标题或提交标题里直接确认，全部记为 unknown。

NetBox 这次没有克隆。Saleor 已经有两类场景同时满足「反复出现、类型不止一种、能够解析」。
