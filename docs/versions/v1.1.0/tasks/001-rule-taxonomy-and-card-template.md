# 001：规则分类体系重构与规则说明卡片规范

## 目标

建立毕业论文可直接使用的规则登记规范。以后新增一条规则时，必须能够说明：制定原因、规则分类、检测定义、依赖范围、输出证据、限制与反例、理论依据，以及后续如何验证有效性。

本迭代不扩充全部规则，也不把草案规则接入现有执行引擎。v1.0.0 的四条粗粒度演示规则不纳入本登记册；它们只属于历史流程展示，不作为当前规则模型的资产。

## 分类决策

规则首先按 `rule_family` 分为三个紧扣研究题目的知识域：

- `code_smell`：通用代码异味与语法陷阱；
- `backend_contract`：后端框架与安全契约；
- `breaking_impact`：变更破坏性与兼容冲击。
- 变更规模、文件数量、模块数量、Hunk 数和测试协同等内容不是独立规则阵营，而是规则的机器触发特征。它们可以组合成通用规则，例如“变更规模过大”。

`rule_family` 只表示知识域，不表示生命周期。风险性质、依赖层级、目标层、证据类型、严重度和一票抬升是独立属性。

## 标签边界

- `risk_nature` 必须是 `pr_intrinsic` 或 `external_impact`。规则即风险探测器，不使用 `none`；若规则只描述变更自身的结构风险，使用 `pr_intrinsic`。
- `dependency_level` 表示判定依赖的技术层级：`language`、`framework`、`database`、`process`。它与规则阵营有映射但不等同：代码异味通常依赖语言或过程指标，后端契约依赖框架，破坏性冲击通常依赖数据库或过程指标。
- `target_layer` 表示系统实际分析的对象层：`ast_syntax`、`diff_delta`、`call_graph`、`change_metadata`。
- `evidence_type` 表示向用户展示、供人工复核的证据形态：`code_slice`、`symbol_pair`、`metric_value`。它不应重复填写分析层名称。
- `trigger_features` 必须登记为机器可计算字段，至少包含名称、来源、值类型和比较操作；修改行数、文件数、模块数等应记录为结构化特征，不能只写自然语言短语。

## 有效性责任

本迭代只登记验证义务和后续验证计划，不宣称草案规则已经有效。

- 通用规则需要说明权威文献、CWE、OWASP 或语言文档依据，并用构造样例验证检测器实现；
- 后端契约规则需要说明框架约束，并在后续迭代使用真实 PR、人工标注和已知案例验证；
- 变更规模类通用规则需要说明各触发特征、组合逻辑和阈值依据；修改行数、文件数等原始值作为 Finding 的上下文证据保留。

引用文献只能支持规则思想的理论依据，不能替代对本项目检测实现的测试或实证验证。

## 兼容性

本迭代不改变 `stage05.v1` 规则结果、不增加执行引擎规则、不改变评分配置和现有 API。登记册位于后端数据目录，但目前只是研究与规划资料，系统启动时不会加载它；后续接入运行时必须单独实现并补充测试。

## 验收标准

- 分类字典、标签枚举和严重度/一票抬升含义已经固定；
- 每条计划规则都有登记条目；
- 每条登记条目都包含制定理由、检测定义、依据、限制和验证义务；
- 现有四条演示规则已明确排除出当前登记册；
- 规则卡片可以直接复制用于论文中的单条规则说明；
- JSON 登记册可由自动化测试读取并检查必填字段与枚举值。

## 当前遗留

- 三类正式规则尚未全部接入检测器；
- 文献引用的具体 DOI、CWE 编号和版本需要在论文调研阶段逐条补齐；
- Precision、Recall 和已知案例覆盖率属于后续实证任务，不在任务 001 中提前给出结果。
